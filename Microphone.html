Mikro für RehaLingo

Ziel: Überblick, Annahmen und nächste Schritte, um das blockierte Mikro/ASR auf dem iPad zu debuggen und produktionsreif zu machen.

Kurzfassung

  • Mikro/ASR nutzt speech_to_text 6.6.2 + permission_handler (Mikrofon + Speech), gekapselt in lib/logic/naming_controller.dart + lib/logic/voice_state.dart und getriggert aus lib/app/robulingo_app.dart.
  • Auf dem aktuellen iPad fehlt Developer Mode; daher konnte die System-Permission nicht sauber erteilt/getestet werden (Verdacht: iPadOS <16, MDM oder ScreenTime blockiert den Dev-Mode).
  • UI fällt aktuell mit Skip/Weiter auf 2AFC zurück, wenn Mic/Speech verweigert wird; wir unterstellen, dass Berechtigungen später oder auf anderem Gerät funktionieren.

Grundannahmen & Vermutungen

  • Ohne Developer Mode lässt sich der Build nicht als vertrauenswürdige Dev-App starten; dadurch erscheinen entweder keine Permission-Dialoge oder die Status-API meldet dauerhaft abgelehnt.
  • iPadOS 16+ erforderlich; MDM/ScreenTime kann Developer Mode und Mikrofon/Speech blockieren.
  • speech_to_text benötigt funktionierende Apple Speech Services (Siri/Dictation, Online-Fallback). Fehlende Netzwerkfreigabe oder deaktivierte Diktierfunktion kann als no_match / notAuthorized auftauchen.
  • Im Code ist der Simulator-Fallback deaktiviert (assumeIOSDebugSim = false), d. h. ein permanentlyDenied blockiert sofort.

    Future<MicInitResult> ensureMicReadyDetailed() async {
  const bool assumeIOSDebugSim = false;
  final micStatus = await Permission.microphone.request();
  PermissionStatus speechStatus = PermissionStatus.granted;
  if (Platform.isIOS || Platform.isMacOS) {
    speechStatus = await Permission.speech.status;
    if (!speechStatus.isGranted && !speechStatus.isPermanentlyDenied) {
      speechStatus = await Permission.speech.request();
    }
  }
  if (!micStatus.isGranted || !speechStatus.isGranted) {
    return MicInitResult(ready: false, ...);
  }
  final ok = await speech.initialize(onStatus: onStatus, onError: onError);
  return MicInitResult(ready: ok && micStatus.isGranted, ...);
}

Aktueller Status / Problem

  • Auf dem Ziel-iPad fehlt (noch) der Developer Mode → kein sauberer Deployment-/Permission-Flow, vermutlich deshalb permanentlyDenied oder kein Dialog.
  • Keine validierte Messung, ob Permission.speech / Permission.microphone tatsächlich erteilt werden; ASR auf macOS lief, aber iOS-Gerät wurde nicht bestätigt.
  • Simulator-Fallback ist bewusst aus (kein „trotz permanent deny weitermachen“), dadurch blockt jeder echte Deny.

Wie wir das Problem aktuell ausklammern

  • Benennen blockiert bei verweigertem Mic/Speech; UI bietet „Weiter“ (Skip) und „Einstellungen öffnen“, sodass der restliche 2AFC-Flow weiterläuft.
  • Wir gehen davon aus, dass ein späteres oder anderes Gerät (mit Developer Mode + erlaubten Berechtigungen) den Flow freischaltet; bis dahin bleibt namingHold/micDenied gesetzt.
  • Falls nötig für Tests ohne echte Permissions: assumeIOSDebugSim (in ensureMicReadyDetailed) könnte temporär auf true gesetzt werden, um permanentlyDenied zu ignorieren – nur als Dev-Hack, nicht für Produktion.
  • namingDisabled (State in VoiceState) kann gesetzt werden, um Benennen komplett auszuschalten und nur 2AFC laufen zu lassen.

Nächste Schritte für Engineers

  1. Device fixen: iPad auf iPadOS 16/17 aktualisieren, Developer Mode freischalten (oder MDM/ScreenTime entfernen), dann Build via Xcode installieren und Trust-Dialog bestätigen.
  2. Permissions testen: MicProbePage und NamingDemoScreen auf dem Gerät starten; erwarteter Status: Mic/Speech granted, SpeechToText.initialize() liefert ok=true, isAvailable=true.
  3. ASR-Status sammeln: Debug-Logs ([naming][perm], [naming][init], [asr][error]) aus robulingo_app.dart/naming_controller.dart prüfen; falls restricted/notAuthorized, iOS-Einstellungen checken (Siri & Diktierfunktion, Datenschutz > Sprache & Region).
  4. Locale-Recheck: Falls ASR nicht startet, erneut mit explizitem Locale (_speechLocaleFor(lang)) testen; derzeit auskommentiert, um iOS nicht zu blockieren.
  5. Fallback-Plan: Wenn speech_to_text auf iPad nicht stabil läuft, Evaluate Alternativen (z. B. native SFSpeechRecognizer via MethodChannel oder Remote-ASR über Backend) und vergleichen.
