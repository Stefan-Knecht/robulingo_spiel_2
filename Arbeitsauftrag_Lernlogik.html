Arbeitsauftrag Lernlogik – Comprehension & Naming 


Ziel: Implementiere eine offline-first Lernlogik für ein mobiles Sprachlernspiel mit zwei getrennten Fähigkeiten/Tracks:

• Comprehension (C / 2AFC-Verstehen): Item wird erkannt/zugeordnet.

• Naming (N / Benennen): Item wird aktiv benannt (Voice/ASR), separat von Comprehension.


Beide Tracks haben eigene Zustände, eigene Queues, eigene Kennzahlen. Naming darf Comprehension nicht zurückwerfen.


⸻


0) Begriffe und Leitplanken

• Zeitmaß = Slots: slotIndex ist ein globaler Zähler, der pro Trial (egal welcher Track) steigt.

• Offline-first: Persistenter State ist die Wahrheit; Logs sind append-only für Monitoring/Debug/Analytics.

• Heuristiken statt komplexer Modelle: Streak-Regeln + Queue-Injektion + harte Limits gegen Frust.

• ASR-Noise: Wird pragmatisch über tolerant gestaltete Matching-Regeln abgefedert (z.B. Transcript→Levenshtein, oder anderer toleranter Matcher).


⸻


1) Datenhaltung (Offline-first)


1.1 GlobalState

• slotIndex: int (monoton, sessionübergreifend)

• Comprehension

• c_recap1Q: deque<uuid>

• c_recap2Q: deque<uuid>

• c_remedQ: deque<uuid>

• Naming

• n_recap1Q: deque<uuid>

• n_recap2Q: deque<uuid>

• n_remedQ: deque<uuid>

• n_backlog: stack<NamingSessionSnapshot> (LIFO)

• n_backlog_cap = 5

• activeNeighborhoodPointer o.ä. (falls nötig für euer ±5 Nachbarn-Active-System)


Queue-Regel: keine Duplikate; push idempotent; Stage und Queue konsistent halten.


⸻


1.2 ItemState (pro uuid)


ComprehensionState (C)

• c_stage: C_ACTIVE | C_RECAP1 | C_RECAP2 | C_REMED | C_MASTERED

• c_lastSeenSlot: int

• Streak-/Fensterwerte:

• c_last5: ringbuffer<bool> (oder c_streak5)

• c_last3 / c_last2 (oder Streakzähler pro Stage)

• c_activeAttemptsWindow: int (bis max 16)

• c_activeCorrectWindow: int (bis max 16)

• Optional Bayesian Memory (wenn ihr es drin habt):

• c_alpha: float, c_beta: float


NamingState (N)

• n_stage: N_ACTIVE | N_RECAP1 | N_RECAP2 | N_REMED | N_MASTERED

• n_lastSeenSlot: int

• Streak-/Fensterwerte:

• n_last5, n_last3, n_last2

• n_activeAttemptsWindow: int (bis max 16)

• n_activeCorrectWindow: int (bis max 16)

• Optional Bayesian Memory:

• n_alpha: float, n_beta: float


⸻


2) Comprehension (2AFC) – Policy


2.1 Slot Scheduler (Comprehension)


Für jeden Slot, wenn Comprehension läuft:

• Wenn slotIndex % 40 == 0 und c_remedQ nicht leer → ziehe daraus.

• Sonst wenn slotIndex % 20 == 0 und c_recap2Q nicht leer → ziehe daraus.

• Sonst wenn slotIndex % 10 == 0 und c_recap1Q nicht leer → ziehe daraus.

• Sonst → C_ACTIVE (normale Item-Präsentation mit ±5 Nachbarn).


Priorität bei Kollision: REMED(40) > RECAP2(20) > RECAP1(10) > ACTIVE.

Wenn die bevorzugte Queue leer ist → fallback nach unten.


⸻


2.2 Transitions (Comprehension)


Stage Kriterium Transition Aktion

C_ACTIVE letzte 5/5 korrekt → C_RECAP1 push c_recap1Q

C_RECAP1 letzte 3/3 korrekt → C_RECAP2 push c_recap2Q

C_RECAP2 letzte 2/2 korrekt → C_MASTERED aus allen C-Queues entfernen

C_ACTIVE attempts==16 und correct<12 → C_REMED push c_remedQ

C_REMED wieder 5/5 korrekt → C_RECAP1 push c_recap1Q


Wichtig: Comprehension ist unabhängig von Naming.


⸻


2.3 (Optional) Decay/Bayes “Moving Prior”


Wenn ihr es nutzt:

• Vorannahme: m (z.B. 0.5), Sicherheit kappa

• alpha0=m*kappa, beta0=(1-m)*kappa

• Bei jedem Trial:

1. Decay Richtung Prior abhängig von Δslots

2. Update: correct → alpha += 1 else beta += 1

3. lastSeenSlot = slotIndex


(Die Heuristik-Regeln funktionieren auch ohne Bayes; Bayes ist optional.)


⸻


3) Naming – Policy (eigene Queues/Stages)


3.1 Naming ist “pure mode” in Sessions


Naming läuft in Naming-Sessions (Blocks) mit:

• maxChallengesPerBlock = 70

• perItemCapPerBlock = 12 (ein Item darf einen Block nicht dominieren)


Ihr bewertet im Naming ausschließlich Naming (ASR/Matcher → correct=true/false).


⸻


3.2 Naming-Pool pro Session (7 Items, random order)


Bei Fresh Naming Session:

• seed5: 5 Items, die Naming freischalten (die 5 Items aus Comprehension, die das Kriterium erfüllt haben)

• Pool-Target: 7 Items

• Extras:

• extraA: 1 Item aus n_recap1Q falls vorhanden

• extraB: 1 Item aus n_remedQ, sonst aus n_recap2Q, falls vorhanden

• Wenn Extras fehlen → Pool bleibt kleiner oder wird aus seed5 aufgefüllt.


Reihenfolge: “fresh shuffle each round”

• Ihr shufflet den Pool vollständig.

• Wenn Pool einmal durch ist → neu shufflen.

• Items, die perItemCap erreicht haben, werden beim nächsten Shuffle ausgeschlossen.


⸻


3.3 Naming-Transitions (analog, aber getrennt)


Stage Kriterium Transition Aktion

N_ACTIVE letzte 5/5 korrekt → N_RECAP1 push n_recap1Q

N_RECAP1 letzte 3/3 korrekt → N_RECAP2 push n_recap2Q

N_RECAP2 letzte 2/2 korrekt → N_MASTERED aus allen N-Queues entfernen

N_ACTIVE (optional) attempts==16 und correct<12 → N_REMED push n_remedQ

N_REMED wieder 5/5 korrekt → N_RECAP1 push n_recap1Q


Per-Item Cap (Block-lokal):

• Wenn attemptsThisBlock[item] == 12: Item für den Rest des Blocks pausieren (nicht mehr ziehen).


⸻


3.4 Scoring im Naming (ASR/Matcher)


Naming braucht nur:

• correct: bool


Wenn ihr Transcript-Text habt: tolerant via Normalisierung + Levenshtein.

Wenn ihr keinen Text habt: threshold auf confidence/similarity eures Voice-Matchers.

Wichtig ist nur: deterministisch loggen, damit ihr später prüfen könnt, ob die Policy “funktioniert”.


⸻


4) Snooze/Resume für Naming (Aphasie-tauglich, ohne Dialoge)


4.1 UI-Elemente

• Zu Beginn jeder Naming-Session: Button mic_delay.webp

• Tap = Snooze: Naming wird sofort abgebrochen und als Snapshot gespeichert.

• Während Comprehension dauerhaft sichtbar: Button mic_restart.webp

• Tap = Resume: springt sofort in die zuletzt geskipte Naming-Session (LIFO).


Keine Rückfragen. Kein “bist du sicher”.


⸻


4.2 Backlog (cap 5) + “letzte übersprungene Session”


Ihr speichert Naming-Sessions als resume-fähige Snapshots:

• n_backlog: stack<NamingSessionSnapshot> (LIFO: letzter Snooze = erster Resume)

• Cap: max 5

• Bei Push, wenn >5 → älteste Session droppen (bottom).


NamingSessionSnapshot (minimal für “komplett zugreifen”)

• snapshot_id: string

• created_slot: int

• pool_item_ids: list<uuid> (<=7)

• max_challenges: 70

• blockTrialsDone: int

• attemptsThisBlock: map<uuid,int>

• optional: correctThisBlock: map<uuid,int>

• (Optional, nur falls ihr „nahtlos“ fortsetzen wollt:)

• rng_seed / round_order / round_index


Einfachste Variante (robust): Beim Resume neu shufflen; Pool bleibt gleich.

Das ist nicht „bitgenau fortsetzen“, aber vollständig “auf die letzte Session zugreifen” bleibt wahr: gleicher Pool, gleicher Fortschritt, gleiche Caps.


⸻


4.3 Semantik “Peek vs Pop” (nur Naming-Queues)


Beim Bauen des 7er-Pools aus n_recap1Q / n_remedQ / n_recap2Q:

• Peek (empfohlen): Item als Kandidat in Pool aufnehmen, Queue nicht verändern.

• Pop: Item aus Queue entfernen, sobald es in Pool aufgenommen wird.


Empfehlung für euer Setup:

Planung mit Peek (sonst “verschwindet” ein Queue-Item, wenn User sofort snoozed).

Wenn ihr “Queue bedienen” streng zählen wollt: Pop erst beim tatsächlichen Präsentieren eines Items, nicht beim Planen.


⸻


5) Regel: “Nie mehr als zwei Naming-Sessions hintereinander”


Wenn Naming automatisch getriggert wird:

• Starte eine Fresh Naming Session.

• Wenn n_backlog nicht leer ist, hänge genau eine resumed Session an.

• Maximal 2 Sessions am Stück.


Wenn Nutzer manuell mic_restart drückt:

• Resume genau die letzte geskipte Session (eine Sache pro Klick).


⸻


6) Logging (Append-only, für Monitoring)


Neben euren trial_result Events ergänzt:


Comprehension

• stage_changed(uuid, from, to, slotIndex, reason)

• queue_push(queue, uuid, slotIndex)

• queue_pop(queue, uuid, slotIndex)


Naming

• naming_session_start(mode="fresh|resume", snapshot_id?, slotIndex)

• naming_snooze(snapshot_id, slotIndex, blockTrialsDone, pool_size)

• naming_resume(snapshot_id, slotIndex, blockTrialsDone)

• backlog_drop(snapshot_id, reason="cap_reached")

• optional: naming_session_end(snapshot_id, slotIndex, totalTrialsDone)


Wichtig: State muss offline persistiert werden (Queues + Backlog + per-item states), sonst ist mic_restart nicht zuverlässig.

8) Implementationshinweise (kurz, aber wichtig)

• Trennung C vs N ist nicht optional: separate stages + queues + stats.

• Snooze/Resume muss stateful sein: sonst ist mic_restart nicht “komplett”.

• Backlog cap=5 ist bewusst hart: älteres fällt weg.

• Per-item cap=12 ist euer Frustschutz innerhalb der 70.
